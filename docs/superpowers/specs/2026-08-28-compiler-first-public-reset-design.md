# Compiler-First Public Reset Design

## Purpose

Make `idol.id` present Idol as a working Lua-derived native compiler, not as an ontology directory, speculative syntax showcase, or collection of infrastructure projections.

## Product hierarchy

The public first viewport answers four questions in order: what Idol is, why it matters, what works now, and how to try it. Primary navigation is Compiler, Playground, Graph, Docs, and Live. Library, API, Platform, Repository, Universe, and operational aliases remain secondary tools or projections.

## Capability truth

Homepage examples must be `compiler-accepted` or `compiler-executed` at the exact pinned `clpi/idol` revision. Law-only, historical, foreign, or unverified source may appear only behind explicit non-executable boundaries. Browser code never mints semantic identities or graph edges.

## Visual system

Use high-contrast editorial typography, 16–18px reading copy, broad whitespace, one warm signal color, and monospace only for source and exact machine facts. Dense workbench styling remains appropriate inside Graph, IDE, Live, and Platform, but not on the language homepage. Mobile receives one primary action and one menu, never a horizontally overflowing product strip.

## Delivery and cache law

Stable paths such as `/shared/shell.js` and `/shared/site.css` must revalidate. Only content-addressed asset names may receive one-year immutable caching. A deployment is admitted only when authority, identity, tests, build, Worker validation, and real Chrome interaction gates all pass.

## Permanent refusals

- superseded project names on active public surfaces;
- speculative language examples as homepage defaults;
- runtime DOM patches that rewrite product hierarchy after load;
- browser-inferred semantic identity;
- horizontal document overflow or touch targets below 44px;
- production health when the deployed commit and authority projection disagree.
